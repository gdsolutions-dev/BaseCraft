# Move an application to a server

Database Tools › Move Data › « Vers un serveur » (“To a Server”) opens the « Assistant Migration vers un serveur ». It moves every local table of the open base to a **PostgreSQL** or **SQL Server** database: the structure, the data, the keys, the indexes and the relationships. It then replaces each local table with a linked table of the same name, so forms, reports, queries and macros keep working. Access users know this as the Upsizing Wizard (SQL Server Migration Assistant). The command is in the full application only, not in BaseCraft Runtime.

The linked tables then behave as described in [PostgreSQL linked tables](postgresql.md) and [SQL Server linked tables](sqlserver.md). External Data › Import › PostgreSQL / SQL Server does the reverse for a few tables (see [Import from a server](#import-from-a-server)).

## Before you start

- **A writable base with local tables.** A base opened read-only, a base without local tables, or a shared data file made by Split Database (its front-ends link its tables) is refused before anything is written. Links already in the base stay as they are.
- **A schema that exists.** The wizard never creates a schema (`public` and `dbo` are proposed). No table or view of that schema may have the name of a local table, compared without case: the run is refused and lists them. The wizard never overwrites a server table and never appends to one.
- **A login that may create tables in that schema.** PostgreSQL: `CREATE` on the schema. SQL Server: `CREATE TABLE` and `ALTER` on the schema, plus the right to run `DBCC CHECKIDENT` (the schema's owner, `db_owner` or `db_ddladmin`). The login you type in the wizard becomes the links' login on this workstation (remembered if you tick « Mémoriser »). Every other user logs in with their own login, which needs only `SELECT`, `INSERT`, `UPDATE` and `DELETE`.
- **Names the server accepts.** PostgreSQL cuts names longer than 63 bytes without warning, so the wizard refuses a table or field name longer than 63 bytes in UTF-8 (an accented letter counts 2, a Japanese character 3) and lists them: rename them first. SQL Server's limit (128 characters) is above BaseCraft's 64.
- **Close what you are doing.** Every open document is closed first, as Split Database does.

## The wizard

1. What moves, and the destination: PostgreSQL or SQL Server.
2. The server's connection dialog (server, port, database, user, TLS or encryption mode, password), as for External Data.
3. The schema, then « Migrer ».

A progress dialog shows the table being copied and the records done over the total, with « Arrêter » (Stop). « Finalisation… » follows; Stop is then disabled. At the end the report (see [The report](#the-report)) or the reason nothing was done is shown.

## What moves, and how

### Types

| BaseCraft | PostgreSQL | SQL Server |
|---|---|---|
| AutoNumber (the table's only key) | `integer GENERATED BY DEFAULT AS IDENTITY` | `int IDENTITY(1,1)` |
| Short Text (n) | `varchar(n)` | `nvarchar(n)` |
| Long Text | `text` | `nvarchar(max)` |
| Hyperlink | `text` | `nvarchar(max)` |
| Number Byte | `smallint CHECK (… BETWEEN 0 AND 255)` | `tinyint` |
| Number Integer, Long Integer | `smallint`, `integer` | `smallint`, `int` |
| Number Single, Double | `real`, `double precision` | `real`, `float` |
| Number Decimal (p, s) | `numeric(p,s)` | `decimal(p,s)` |
| Currency | `numeric(19,4)` | `money` |
| Date/Time | `timestamp(0)` | `datetime2(0)` |
| Yes/No | `boolean NOT NULL DEFAULT false` | `bit NOT NULL DEFAULT 0` |

A lookup field keeps its base type. BaseCraft has no Attachment, OLE Object, Calculated or multivalued field, so every field can move.

Three types come back from the server as another type: PostgreSQL's Byte (`smallint`, read as Integer), PostgreSQL's Currency (`numeric(19,4)`, read as Decimal(19, 4)) and Hyperlink on both engines (read as Long Text). BaseCraft keeps the local type on the link (see [BaseCraft's properties travel with the link](#basecrafts-properties-travel-with-the-link)), so the field still shows and behaves as before in BaseCraft. Another program that reads the table sees the server's type. The report lists these fields under « Stocké sous un autre type sur le serveur ».

### Keys, required fields and defaults

- The primary key becomes the table's `PRIMARY KEY`, its fields in design order. Required fields and key fields are `NOT NULL`.
- A Default Value that is a **literal** (a number, a text, a date, Yes or No, a negative number) becomes the column's `DEFAULT`, converted as the field stores it. Any other default (`Date()`, `=[Prix]*2`), and a text default longer than the field, stays in the front-end.
- **Validation rules, Validation Text, a table's validation rule, expression defaults and Allow Zero Length = No stay in the front-end only.** BaseCraft checks them on every write it makes to the linked table, exactly as on a local table, but the server does not know them: another program writing to the table (psql, SSMS, Access through ODBC, a script) bypasses them. The report lists each one under « Appliqué par l'application seulement (pas par le serveur) ». If other programs write to these tables, add the matching `CHECK` constraints on the server yourself.

### Indexes

A field with Indexed = Yes becomes an index named `<table>_<field>`; an index of the Indexes dialog becomes `<table>_<index name>`. Yes (No Duplicates) and unique indexes become unique indexes. A name that the schema (or the run) already uses gets `_2`, `_3`… A name too long for the engine is cut first.

On **SQL Server**, a unique index on fields that accept Null is a **filtered** index (`WHERE … IS NOT NULL`), so the field may hold several Nulls, as in BaseCraft and Access (a plain SQL Server unique index takes one Null only). Two consequences:

- **A unique field that a relationship references** (the « one » side of a relation on a field other than the primary key) cannot use a filtered index: SQL Server requires a plain one there. Such a field may then hold **one Null only**. If it holds several, the run fails with « Le champ … contient plusieurs valeurs Null… » and nothing is kept: give those records values first.
- **Other programs writing to a table with a filtered index** need the session options SQL Server requires for it: `ANSI_NULLS`, `ANSI_PADDING`, `ANSI_WARNINGS`, `ARITHABORT`, `CONCAT_NULL_YIELDS_NULL` and `QUOTED_IDENTIFIER` on, `NUMERIC_ROUNDABORT` off. Current drivers (ODBC Driver 17 and 18, .NET, BaseCraft's) set them; an older tool or a script that turns one of them off gets error 1934 on `INSERT`, `UPDATE` and `DELETE`.

### Relationships

- An **enforced** relationship becomes a `FOREIGN KEY` named as the relationship, with `ON DELETE CASCADE` and `ON UPDATE CASCADE` as its Cascade boxes say, else `NO ACTION`.
- A relationship **not enforced** creates nothing on the server (Access's upsizing does the same); the report lists it.
- **SQL Server refuses cascades that give a table two cascading paths, or a cycle** (a self-referencing relationship counts). Where that would happen, the wizard creates the foreign key with `NO ACTION` for both delete and update, in relationship order, and the report says so for each one (« clé étrangère créée sans cascade… »). On such a relationship, deleting a parent that has children is refused instead of cascading: delete the children first. Update and delete cascades are counted together, as SQL Server does, so a relationship with only one of them checked may be downgraded too. PostgreSQL takes every cascade.
- The front-end's relationships are removed with the local tables (they named local tables). The server's foreign keys now enforce them; BaseCraft reports a refusal by the server as it does on any linked table.

### AutoNumber continuity

AutoNumber values are copied as they are. The server's counter then starts after the largest number BaseCraft ever gave, deleted records included: a number deleted before the migration is never given again, as with a local AutoNumber. The report shows each table's next number. On PostgreSQL the identity is `GENERATED BY DEFAULT`: another program may still give its own value, and the counter does not move then.

### `rowversion` on SQL Server

Each SQL Server table gets a `rowversion` column `bc_rowversion` (`bc_rowversion1`… if a field already has that name). It is not a field in BaseCraft: BaseCraft uses it to detect write conflicts, which are then exact and cheap (see [Locking](sqlserver.md#locking)). The report names it for each table. PostgreSQL tables need none (BaseCraft uses `xmin`).

### Values that cannot move

The run fails, naming the table (and the field when the server says it), and nothing is kept, when a value does not fit the server:

- **SQL Server counts Short Text in UTF-16 units**, BaseCraft in characters: an emoji or another character outside the Basic Multilingual Plane counts twice. A Short Text at its full size that holds one does not fit its `nvarchar(n)`. Make the field longer before migrating.
- **The largest Currency values** (about ±922 337 203 685 477.58 and beyond, up to Currency's limit 922 337 203 685 477.5807) do not reach SQL Server: BaseCraft holds Currency as a double, whose rounding goes past `money`'s maximum (error 8115, out of range).
- **Duplicates the server finds and BaseCraft does not**: on a SQL Server database with a case-insensitive collation (`French_CI_AS`, the usual one), « Lyon » and « LYON » in a field indexed without duplicates are the same value. PostgreSQL compares them with case, as BaseCraft's index does.

## BaseCraft's properties travel with the link

Each link made by the wizard keeps the local field properties: Caption, Description, Format, Decimal Places, Input Mask, Default Value, Validation Rule and Validation Text, Allow Zero Length, the lookup (Row Source, Limit To List…) and Indexed, and the table's Description and validation rule. Datasheets, forms, queries and every write through BaseCraft use them as on the local table: a rule refuses the same values with the same message, Limit To List checks the list (text compared without case, as Access), AutoLookup fills a join's fields. Refresh Link and the Linked Table Manager keep them.

The local type is shown too, as long as the server's column is still the type the wizard created. If someone changes the column on the server (a `varchar(50)` made `varchar(100)`), BaseCraft shows the server's type from then on and keeps the caption, format and rules.

**Design view of a migrated table is read-only**, as for every linked table. To change a caption or a rule, change it on the backup copy and migrate again, or wait for the backlog item that makes these properties editable on the link.

## Safety: the backup, one transaction, the front-end never half-relinked

1. Before anything is written to the server, BaseCraft makes a **backup copy** of the base beside it: `<name>.backup-YYYYMMDD-HHMMSS.basecraft`. It stays in every case, success or failure.
2. Everything on the server happens in **one server transaction**: every table, its rows (in pages of up to 1 000, each a parameterized `INSERT`), its counter, its indexes, then every foreign key. Before the commit, BaseCraft counts each table's rows on the server and compares them with the local count, and reads every table back to check that it can be linked with its key. A difference, a refusal by the server, a lost connection, Stop, or BaseCraft's data process stopping before the commit **leaves nothing on the server**: the server rolls the transaction back.
3. Only after the server's commit does the base change, in **one local transaction**: the relationships removed, every local table removed, every link added, the « Application frontale » option set. If that fails, SQLite rolls it back (the base is as it was) and BaseCraft drops the tables it just created on the server; any it could not drop are named. **The base is never half-relinked**: every table is replaced, or none.

The run's connection has **no statement timeout** (an index or a count on a large table may take long); Stop is always available while the data is copied.

The one transaction holds its locks and its log on the server until the end. It is sized for Access-class files (up to a few GB); a larger copy needs room in the server's transaction log.

### When the outcome is unknown

Two moments cannot be made all-or-nothing between the server and the file:

- **The connection is lost, or « Arrêter » lands, while the server commits** (SQL Server can end with a cancel a commit it already completed). BaseCraft cannot know whether the server kept the tables. It says so (« … on ne sait pas si le serveur l'a enregistrée. La base n'a pas été modifiée. ») and names the tables that may be on the server. The base is unchanged. Check the schema: drop those tables if they are there, then run the wizard again (or link them with External Data if they are complete).
- **BaseCraft's data process is killed between the server's commit and the base's commit** (a few milliseconds): the tables stay on the server and the base is unchanged. The next run is refused with the names of the tables the server already has. Drop them, then run again.

## Stop

« Arrêter » cancels the statement under way on the server; the transaction rolls back and « Migration annulée : rien n'a été modifié. » is shown. Nothing is left on the server, the base is unchanged, and the backup copy stays. Stop is disabled from « Finalisation… » on: the commit is then under way.

## The report

At the end, the report lists:

- the server, the schema and the backup copy;
- each table with its record count, its next AutoNumber and (SQL Server) its `rowversion` column;
- the indexes created (« sans doublons » for a unique one);
- each relationship: foreign key created, created without cascade (SQL Server), or not enforced (nothing created);
- the fields stored as another type on the server;
- the rules kept in the front-end only;
- the queries the server refuses (or, when the check itself fails, that they could not be checked).

« Copier dans le Presse-papiers » copies it as text, one line per entry, to paste in a mail or a document. BaseCraft neither prints nor saves it. No password appears in it.

### Queries are checked, not migrated

Saved queries, forms, reports and macros stay in the front-end. After the switch, BaseCraft **plans** (sends nothing) every saved query and every SQL Record Source of a form or report against the new links, through the same path that runs it, and lists each one the server cannot run with its message, for example « QNoms : Format ne peut pas s'exécuter sur une source PostgreSQL ». Rewrite such a query with the functions of the closed list ([PostgreSQL](postgresql.md#queries-on-the-server-the-closed-list), [SQL Server](sqlserver.md#queries-on-the-server-the-closed-list)), or make it a [pass-through query](postgresql.md#pass-through-queries). Pass-through queries and queries on another server's links are not checked. Queries are never turned into server views or procedures.

## After the migration

- **The base is a front-end.** « Application frontale » (File › Options › Base de données active) is ticked. Put the front-end on the share: BaseCraft Runtime opens it from a local copy on each workstation and takes the new version when you republish it (see [Split database and shared data file](../README.md#split-database-and-shared-data-file)). Give each workstation using the full application its own copy.
- **Several people enter data at the same time.** Each save is checked against the record as it was read: two people changing the same record get the Write Conflict dialog (Save Record, Copy to Clipboard, Drop Changes).
- **Action queries run on the server.** Append, Update and Delete queries on the migrated tables run in one server transaction, every record through the table's rules as locally. A record a rule of BaseCraft refuses is counted by cause and skipped only when you choose to run the query anyway; a record the server refuses (a duplicate key, a missing parent record) rolls the whole query back, even when you run it anyway. An Append that gives AutoNumber values is refused before anything is sent (remove the AutoNumber field from the query: the server numbers the new records). A Make-Table query is refused on a server source: create the table on the server, then fill it with an Append query. On SQL Server tables **without** a `rowversion` column (linked by External Data, not migrated), an Update query does not check whether another user changed a record between the query's read and its write. If the connection is lost while the query runs, whether it completed is unknown: check the table before running it again. In a file whose content is not enabled, action queries stay blocked until « Activer le contenu », as on local tables.
- **Crosstab queries run on the server.** The column headings are read on the server, then merged as Access compares text (« Lyon » and « LYON » are one column); their order follows the server's collation, which may differ from Access's. A column heading with more than 254 values on the server (counted before they are merged) is refused, as a local one with more than 254 is.
- **The Relationships window is empty**: the server's foreign keys enforce referential integrity now.

## Migrating a split application

A shared data file made by Split Database cannot be migrated itself: its front-ends link its tables, and they would link tables that became links. Migrate from **a front-end**: in its Navigation Pane, use Convert to Local Table on each linked table, recreate the relationships in the Relationships window (Convert to Local Table does not bring them), check the result, then run the wizard on that front-end and give it to every workstation. Migrating a data file directly is on the backlog.

## Import from a server

External Data › Import › « PostgreSQL » / « SQL Server » copies server tables into new local tables, without links. The connection dialog lists the server's tables; tick them and « Importer ».

- Each table is named as the link dialog would name it (with `1`, `2`… appended when the front-end already uses the name).
- The fields get the types of the [PostgreSQL](postgresql.md#types) or [SQL Server](sqlserver.md#types) table; the key becomes the primary key, an identity key an AutoNumber that continues after the largest value. Columns BaseCraft cannot read are skipped and listed per table.
- Every table is copied in **one local transaction**: a failure, Stop or a lost connection leaves the base as it was.
- The rows are read in pages, not in one snapshot of the server: import a table when no one is writing to it. A record added during the import can leave another out of the copy, and a table **without a key** can be copied with a record twice and another missing. (A record deleted meanwhile makes the import fail: nothing is kept.)
- What changes on the way: a Null in a `boolean` or `bit` column becomes No (a local Yes/No field holds no Null); a date before 0100-01-01 becomes Null (BaseCraft's date range).
- **Not imported:** indexes other than the primary key, foreign keys, defaults and `CHECK` constraints. Add the indexes and relationships in BaseCraft afterwards.

## Limits

- Every local table moves: there is no list to pick from. A table you wanted to keep local goes to the server too (it stays readable and editable through its link).
- Validation rules, expression defaults and Allow Zero Length are not created on the server (other programs bypass them).
- SQL Server: one Null in a unique field a relationship references; cascades downgraded to `NO ACTION` where SQL Server refuses multiple paths; Short Text counted in UTF-16 units; the largest Currency values; filtered indexes need the standard session options in other programs (error 1934).
- PostgreSQL: names longer than 63 bytes are refused.
- Design view of a migrated table is read-only (backlog).
- Windows and Microsoft Entra authentication to SQL Server are not supported.
